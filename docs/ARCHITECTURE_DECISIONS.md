# 📋 Architecture Decision Records (ADR)

## ADR-001: Multi-Tenancy Model — Shared DB, Separate Schemas

**Date:** 2025-07
**Status:** Accepted

**Decision:** Use PostgreSQL with one database and per-tenant schemas (Model B).

**Reasoning:**
- Model A (shared schema, tenant_id column) risks data leakage between competitors
- Model C (separate DB per tenant) is too expensive at early stage
- Model B gives clean isolation at reasonable operational cost
- Can migrate high-value enterprise tenants to Model C later

---

## ADR-002: UUID Primary Keys Everywhere

**Date:** 2025-07
**Status:** Accepted

**Decision:** All tables use UUID PKs generated by `gen_random_uuid()`.

**Reasoning:**
- Safe to generate in application layer without DB round-trip
- No sequential ID leakage (can't guess record counts)
- Portable across tenant schema merges or migrations

---

## ADR-003: Three Customer Types — Residential, Commercial, HOA

**Date:** 2025-07
**Status:** Accepted

**Decision:** `customer_type` and `job_type` support three values: `residential`, `commercial`, `hoa`.

**Reasoning:**
- HOA contracts behave differently (bulk pricing, common areas, board approval cycles)
- Separating HOA from commercial enables better reporting and pricing logic

---

## ADR-004: Leads Are Separate From Customers

**Date:** 2025-07
**Status:** Accepted

**Decision:** `leads` and `customers` are separate tables. Conversion tracked via `leads.converted_to`.

**Reasoning:**
- Preserves full funnel analytics (lead source, conversion rate, time-to-convert)
- Keeps CRM data clean — not every lead becomes a customer
- Migrated from Integral Exterior prototype's Azure Table Storage leads
